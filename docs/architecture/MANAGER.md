# Game & Module Manager (Phase 2)

This document covers installation profiles, the workspace lifecycle, the asset
index and backup/restore.

## 1. Installation profiles

**Model** (`config/profiles.json`, machine-local, git-ignored):

```json
{
  "schemaVersion": 1,
  "activeId": "warband-cb7328",
  "profiles": [
    {
      "id": "warband-cb7328",
      "label": "Warband",
      "path": "C:/Games/.../Mount and Blade - Warband",
      "createdAt": "2026-11-06T09:53:31.342Z",
      "lastValidatedAt": "2026-11-06T09:53:31.366Z",
      "valid": true,
      "version": "1.170",
      "moduleCount": 3
    }
  ]
}
```

Rules (VERIFIED by tests):

- **Bootstrap**: if no profiles exist, the engine probes `WARBAND_DIR`,
  `config/app.json` and well-known paths, then stores the first valid
  installation as a profile and activates it.
- **Validation**: a profile must contain `mb_warband.exe` and `Modules/`;
  `describeInstallation` reads the engine version from `rgl_log.txt`.
- **Deduplication**: adding the same path twice returns the existing profile.
- **Activation**: switching the active profile reloads modules and clears parsed
  module data (BRF index, items, textures).
- **Removal**: requires the profile id as `confirm`. Removing a profile only
  edits the JSON file; **no game files are touched**.

## 2. Workspaces

Layout:

```
workspace/<id>/.workspace.json
workspace/<id>/.backups/<timestamp>/<relative path>
workspace/<id>/<relative path>
```

`WorkspaceMetadata` records `id`, `label`, `moduleId`, timestamps and a map of
files with `bytes`, `sha256` and `updatedAt`.

Lifecycle:

| Operation | API | Safety |
|---|---|---|
| Create | `POST /api/workspaces` | label slug; never overwrites an existing directory |
| List | `GET /api/workspaces` | metadata only |
| Delete | `DELETE /api/workspaces/:id?confirm=<id>` | typed confirmation; only paths inside `workspace/` |
| Write (engine/CLI) | `WorkspaceStore.writeFile` | relative paths only; atomic; backs up overwritten files |
| Serialize BRF | `engine.exportBrf` | reads the installation, writes into the workspace |

A workspace is the **only** destination for generated bytes. The engine's
`writeFile` resolves the target inside `workspace/<id>/`, rejects `..`,
absolute paths, drive letters and NUL bytes, writes a temp file and renames it,
and records the SHA-256 of the result.

## 3. Asset index

The engine exposes the merged BRF index as a browsable catalogue:

- **Meshes**: name, family (base/LOD/pieces), material, vertex layout, vertex
  and face counts, rigging flag, source BRFs, items that use the base mesh.
- **Materials**: shader, flags, specular, colour, texture references, meshes
  that use it.
- **Textures**: BRF declarations, disk file, DDS dimensions/format/mipmaps,
  materials that reference it.
- **Shaders**: source BRFs and materials that use them.

Endpoints:

```
GET /api/resources?module=Native&type=mesh|material|texture|shader&q=&limit=&offset=
GET /api/resources/:type/:name?module=Native
```

The UI (`Recursos`) mirrors this with a filterable list, a detail panel and a
cross-reference panel. Clicking an item reference jumps to that item in the
outfit view.

## 4. Backups and restore

| Kind | Location | Metadata | Restore |
|---|---|---|---|
| Project | `backups/projects/<id>.<stamp>.json` | full project JSON + SHA-256 | `POST /api/backups/restore {kind:'project', path, confirm:<id>}` |
| Workspace file | `workspace/<id>/.backups/<stamp>/<rel>` + `<rel>.json` sidecar | sidecar stores `workspace`, `file`, `sha256`, `bytes`, `backedUpAt` | `POST /api/backups/restore {kind:'workspace', workspaceId, path, confirm:<id>}` |

Guarantees (tested):

- Listing never hides other backups because one is corrupt.
- Restore requires the entity id as `confirm`; a wrong value returns 400.
- A workspace restore verifies the backup SHA-256 **before** writing.
- Restoring first backs up the current file, so the restore itself is
  reversible.
- Restore paths must stay inside the corresponding backup root.
- Project restore validates `schemaVersion` and that the id matches.

Retention: Phase 2 keeps **all** backups. Pruning is deferred to Phase 9.

## 5. UI

| View | Purpose |
|---|---|
| `Prendas` | existing clothing/armor browser (items + chain + validation) |
| `Recursos` | asset index (meshes, materials, textures, shaders) |
| `Workspaces` | create/list/delete workspaces |
| `Copias` | project and workspace backup catalogue with restore |
| Modal ⚙ | installation profiles: add, activate, validate, remove |

The header exposes the active installation profile and the module selector.

## 6. Limits / out of scope

- Workspace deletion is implemented in the engine/UI, but there is no
  workspace **rename** or file-level delete yet.
- No diff preview before restore (the exact file/path and hash are shown).
- No auto-pruning of old backups.
- The asset index shows LOD/piece meshes as separate rows (grouping is a UI
  enhancement, not a data limitation).
- Module deployment is still Phase 8.
